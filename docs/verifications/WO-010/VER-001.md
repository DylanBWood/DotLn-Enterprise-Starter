## 2. Review the implementation

comparison script and the evidence under `docs/evidence/WO-010/`. It
replaces the profile's "after WO-010 merges" sentence, sets the release
claim and heading to `v0.3.1`, and regenerates projections. No changed path
is in `KIT-MANIFEST.json`, and the code identity equals WO-009's integrated
one, so no launchpad code changed, as the patch classification says.

The ruleset files are the Design's documents, with one addition: an empty
`exclude` list, which the server returns anyway. The script is 36 lines
against the Design's estimate of about 20. It requires unique types on both
sides and equal lengths, so its type sets are equal, and it compares each
expected parameter with `isDeepStrictEqual`. It fails closed on every
malformed input I gave it. I see nothing simpler with the same contract.

One improvement, not a defect: the script has no header saying it
compares rule types and expected parameters only. The evidence README says
so, but the planning receipt read a stronger contract into the order, which
is how F1's condition came to be written. A one-line header comment would
tell the next reader what the script leaves to the ruleset readbacks.

The evidence keeps API readbacks, the operator's screenshot and the
operator's attestation apart. It does not present the fork's hidden
`bypass_actors` as an empty list. The fork's ruleset was created through
the owner's web login before the order ran (operator attestation). The
order's Design admits that route: the file's rules are the checklist and
the readback is the same. The fork's history endpoint is closed to this
account, so the creating account stays an attestation.

Disclosure: `compare-rules.mjs` is both under verification and the
instrument that printed the executor's `match` results. I did not rest
criteria 2 and 4 on it alone. The live readbacks are byte-identical to the
committed ones, and a separate script printed every declared parameter
